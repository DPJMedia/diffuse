# Image display issue — summary for team diagnosis

## Setup

- **App:** Next.js app (diffuse.ai) with a dashboard where users manage **projects**, **inputs** (recordings, documents, images), and **outputs** (generated articles with optional cover images).
- **Workflow:** n8n workflow is triggered when the user clicks **Generate**. We POST to an n8n webhook with project_id, user_id, inputs, options, etc. n8n runs the workflow (e.g. article generation + image generation via DALL·E or similar) and **returns the full response in the same HTTP request** (synchronous webhook).
- **Image source:** The image is generated by a node in n8n (e.g. DALL·E) and is hosted on **Azure Blob Storage** at a URL like:
  `https://oaidalleapiprodscus.blob.core.windows.net/private/org-.../user-.../img-....png?st=...&se=...&sig=...`
- **Storage:** We use **Supabase** for app data (projects, outputs) and for file storage (bucket `project-files` for cover images and project assets). Output rows have a `cover_photo_path` column (path in that bucket) and optional `workflow_metadata` (JSON, e.g. `generated_image_url`).
- **Display:** The **Output Details** modal shows the article and a **cover image**. The image is loaded either from our API (`/api/project-file?path=...` for files in our bucket) or, when we only have an external URL, via a proxy (`/api/proxy-image?url=...`) that fetches the image server-side and streams it to the client.

---

## What we’re trying to do

1. When the user runs **Generate**, the workflow produces:
   - Article content (title, body, excerpt, etc.)
   - A **generated image** (e.g. from DALL·E), available as a URL (and optionally as base64 or a Supabase path).
2. We want to:
   - Save the output (article + reference to the image) in the DB.
   - **Show the generated image** in the Output Details modal for that output.
   - Prefer storing the image in **our Supabase bucket** so we’re not dependent on external URLs (expiry, DNS, CORS).

---

## What we’re expecting

- **Every** run that produces an image in n8n should result in:
  - The output row having either:
    - `cover_photo_path` set (path in our bucket), **or**
    - `workflow_metadata.generated_image_url` set (external URL), so we can at least try to show it (e.g. via proxy).
  - The **Output Details** modal showing the cover image (from our bucket or via proxy), with no broken image or console errors.

---

## What we’re hitting

### 1. Image doesn’t display in the app (browser)

- **Symptom:** Output Details shows an empty/grey area where the cover image should be. Console shows:
  - `Failed to load resource: net::ERR_NAME_NOT_RESOLVED`
  - Request URL: `https://oaidalleapiprodscus.blob.core.windows.net/...`
- **Cause:** The browser (and sometimes our server) **cannot resolve the hostname** `oaidalleapiprodscus.blob.core.windows.net` (DNS/network). So when we used that URL directly as the image `src`, the request failed. Pasting the same URL in a new browser tab can work on some networks; in the app context (or on Vercel) it often does not.
- **Mitigation in place:** We no longer use the Azure URL directly. When we only have that URL, we load the image via **our** API: `/api/proxy-image?url=...`. The **server** fetches the image and streams it to the client. If the server also can’t reach Azure, the proxy returns 502 and the image still won’t show.

### 2. Many outputs have empty `workflow_metadata` (no image URL in DB)

- **Symptom:** In `diffuse_project_outputs`, most rows have `workflow_metadata = {}` even though n8n executions clearly show an image URL in the workflow.
- **Cause:** Our API **extracts** the image URL (or base64, or Supabase path) from the **webhook response body**. If the URL lives in a different node or a different shape than we expect (e.g. nested under another key, or in a sibling node that isn’t merged into the final response), we don’t find it. So we never set `workflow_metadata.generated_image_url` (and we don’t run fetch-and-store or proxy for that output).
- **Result:** No image URL in the DB → no cover image to show (and no attempt to fetch/store or proxy).

### 3. When we do have the URL, fetch-and-store often doesn’t run or fails

- **Symptom:** Some rows have `workflow_metadata.generated_image_url` set but `cover_photo_path` is still null (or only the project cover). Image may or may not show (depending on whether the proxy works).
- **Cause:** After creating the output row, we try to **fetch** the image from that URL (server-side) and **upload** it to Supabase `project-files`, then update the row with `cover_photo_path`. This fails when:
  - The **server** can’t resolve the Azure hostname (same ERR_NAME_NOT_RESOLVED on the server), or
  - The fetch times out or returns an error, or
  - The upload to Supabase fails (permissions, path, bucket).
- **Result:** We have the URL in the DB but no local file; we fall back to the proxy, which may also fail if the server can’t reach Azure.

### 4. Inconsistent behaviour between “paste URL in browser” and “load in app”

- **Observation:** The same Azure URL works when pasted in the browser but fails in the app (or on Vercel).
- **Explanation:** Different **context**: machine, DNS, network, or origin. The app (and our server) may be in an environment where that hostname doesn’t resolve or isn’t reachable. So “it works when I paste it” doesn’t guarantee it will work for the app or for all users.

---

## Summary for diagnosis

| Area | What to check |
|------|----------------|
| **Why no image in DB for most runs?** | Confirm the **exact shape** of the webhook response n8n returns (top-level keys, which node’s output is in the body). Ensure the image URL (or base64 or Supabase path) is present in that response in a place our extraction logic checks. |
| **Why doesn’t the image show in the UI?** | If we have only the Azure URL: we use the proxy. Check whether the **proxy** request (`/api/proxy-image?url=...`) returns 200 or 502. If 502, the server can’t fetch the Azure URL. If 200 and the image still doesn’t show, check UI/network (CORS, CSP, or wrong URL used). |
| **Why doesn’t fetch-and-store run or succeed?** | Check **server logs** for: “Found image URL”, “Generated image saved to storage”, “Failed to persist generated image”, “Generated image fetch failed”. That tells you whether we found the URL and whether fetch or upload failed. |
| **Long-term fix** | Prefer **not** depending on our server or the browser loading Azure. Either: (a) have n8n send the image as **base64** in the webhook response (we upload to Supabase), or (b) have n8n **upload the image to Supabase** and return the **storage path** in the response (we set `cover_photo_path` and serve from our bucket). |

---

## Current code behaviour (short)

- We **insert** a new output row every Generate; we set `workflow_metadata` only if we find an image URL (or path) in the response; we set `cover_photo_path` to the project cover or to a path from the workflow if provided.
- We **search** the full n8n response for: (1) a Supabase storage path, (2) base64 image data, (3) an image URL. We accept several key names for each.
- If we find a **Supabase path** in the response, we use it as `cover_photo_path` and do nothing else for the image.
- If we find **base64**, we decode, upload to `project-files`, and set `cover_photo_path`.
- If we find only a **URL**, we try to fetch it server-side, upload to `project-files`, and set `cover_photo_path`; if that fails, we keep `workflow_metadata.generated_image_url` and the UI uses the **proxy** for that URL.
- **Display order:** We show the image from (1) user-uploaded cover, (2) `cover_photo_path` via `/api/project-file`, (3) `workflow_metadata.generated_image_url` via `/api/proxy-image`. We never set the img `src` to the raw Azure URL.

This doc should be enough for the team to align on setup, goals, and where to look when diagnosing why an output has no image in the DB or why the image doesn’t display.
